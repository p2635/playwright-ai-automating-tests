# Login Test Plan

- Version: 0.1
- Generated by Phil on 22 September 2026
- Reviewed by Phil: Version 0.1 reviewed 22 September 2026

## Feature Overview

BuggyBoard requires users to authenticate with a username and password on the `/login` page before accessing any protected page, and persists the session across page refreshes.

## Test Scenarios

### 1. Login page display and route protection

#### 1.1. Displays the login page with its required fields

**Preconditions:**

1. The user is not authenticated (no active session/local storage).

**Steps:**

1. Navigate to `/login`.

**Expected Results:**

1. The login page is displayed. [03-AC1]
2. A `Username` field is visible. [03-AC1]
3. A `Password` field is visible and masks its input (`type="password"`). [03-AC1]
4. A `Login` button is visible. [03-AC1]

#### 1.2. Redirects unauthenticated users to the login page

**Preconditions:**

1. The user is not authenticated.

**Steps:**

1. Navigate directly to a protected page, such as `/board`.

**Expected Results:**

1. The app redirects to `/login`. [03-AC2]

### 2. Successful login

#### 2.1. Logs in with valid credentials

**Preconditions:**

1. The login page is displayed.

**Steps:**

1. Enter a valid username and password from `users.json` (e.g. `buggy` / `1970beetle`).
2. Click the `Login` button.

**Expected Results:**

1. The user is authenticated. [03-AC3]
2. The app navigates to `/board`. [03-AC3]

#### 2.2. Submits the login form by pressing Enter in either field

**Preconditions:**

1. The login page is displayed.

**Steps:**

1. Enter a valid username and password.
2. Press Enter while focused on the `Username` field; repeat the scenario pressing Enter while focused on the `Password` field.

**Expected Results:**

1. Pressing Enter in the `Username` field submits the form and logs the user in, navigating to `/board`. [03-AC4]
2. Pressing Enter in the `Password` field submits the form and logs the user in, navigating to `/board`. [03-AC4]

#### 2.3. Trims leading and trailing whitespace from the username

**Preconditions:**

1. The login page is displayed.

**Steps:**

1. Enter a valid username with leading and trailing whitespace (e.g. `  buggy  `) and its correct password.
2. Click the `Login` button.

**Expected Results:**

1. The whitespace is trimmed from the username before it is validated. [03-AC10]
2. Login succeeds and the app navigates to `/board`. [03-AC10]

### 3. Failed login and validation errors

#### 3.1. Rejects an invalid username

**Preconditions:**

1. The login page is displayed.

**Steps:**

1. Enter a username that does not exist in `users.json` (e.g. `baduser`) and any password.
2. Click the `Login` button.

**Expected Results:**

1. The user remains unauthenticated and on `/login`. [03-AC5]
2. A generic error alert reading `Invalid username or password.` is displayed. [03-AC5]

#### 3.2. Rejects an invalid password

**Preconditions:**

1. The login page is displayed.

**Steps:**

1. Enter a valid username (e.g. `buggy`) with an incorrect password.
2. Click the `Login` button.

**Expected Results:**

1. The user remains unauthenticated and on `/login`. [03-AC6]
2. The same generic error alert reading `Invalid username or password.` is displayed, not revealing which field was wrong. [03-AC6]

#### 3.3. Rejects a blank username

**Preconditions:**

1. The login page is displayed.

**Steps:**

1. Leave `Username` blank and enter any value into `Password`.
2. Click the `Login` button.

**Expected Results:**

1. The user remains unauthenticated. [03-AC7]
2. An error alert reading `Username cannot be blank.` is displayed. [03-AC7]

#### 3.4. Rejects a blank password

**Preconditions:**

1. The login page is displayed.

**Steps:**

1. Enter a valid username and leave `Password` blank.
2. Click the `Login` button.

**Expected Results:**

1. The user remains unauthenticated. [03-AC8]
2. An error alert reading `Password cannot be blank.` is displayed. [03-AC8]

#### 3.5. Rejects blank username and password together

**Preconditions:**

1. The login page is displayed.

**Steps:**

1. Leave both `Username` and `Password` blank.
2. Click the `Login` button.

**Expected Results:**

1. The user remains unauthenticated. [03-AC9]
2. An error alert reading `Please enter your username and password.` is displayed, distinct from the single-field blank messages. [03-AC9]

### 4. Authenticated session behavior

#### 4.1. Redirects an authenticated user away from the login page

**Preconditions:**

1. The user is authenticated (see Seed / Fixture Guidance).

**Steps:**

1. Navigate to `/login`.

**Expected Results:**

1. The app redirects to `/board` instead of showing the login form. [03-AC11]

#### 4.2. Persists the session across a page refresh

**Preconditions:**

1. The user is authenticated and the `/board` page is displayed.

**Steps:**

1. Refresh the page.

**Expected Results:**

1. The user remains authenticated. [03-AC12]
2. The `/board` page remains displayed without redirecting to `/login`. [03-AC12]

## Out of Scope (deferred)

- Logout behavior, session invalidation, and the browser-back-button-after-logout flow are covered by a dedicated logout test plan per `specs/features/05-logout.md`, not here.
- Per-field visual validation states (e.g. field-level red outlines) beyond the alert text are not specified in `specs/features/03-login.md` and are not asserted.

## Technical Information

### Seed / Fixture Guidance

Use `tests/seed.spec.ts` / `tests/pages/login.page.ts` as the pattern for authenticating as the `buggy` user (from `users.json`) and verifying navigation to `/board`. For scenarios that require an authenticated starting state (Section 4), log in via the `LoginPage.login()` helper in a `beforeEach` before exercising the scenario. Failed-login scenarios (Section 3) do not require any seeded data beyond the static `users.json` file and should start from a fresh, unauthenticated browser context.

### Locator Guidance

Prefer accessible Playwright locators: `page.getByLabel('Username')`, `page.getByLabel('Password')`, `page.getByRole('button', { name: 'Login' })`, and `page.getByRole('alert')` for error messages. Assert error text with an exact or `toHaveText` match against the alert locator rather than searching the whole page body. Use `expect(page).toHaveURL(...)` to confirm redirects to `/login` or `/board`.
