# BuggyBoard Board Search Test Plan

- Version: 0.1
- Generated by Phil on 22 September 2026
- Reviewed by Phil: Version 0.1 reviewed 22 September 2026

## Feature Overview

BuggyBoard's board page includes a live search field for filtering bugs by title.

## Test Scenarios

### 1. Board search and state-filter workflows

#### 1.1. Shows all visible bugs in the default active state when search is blank

**Preconditions:**

1. Authenticate with the seed and load the fixture set (see Seed / Fixture Guidance).

**Steps:**

1. Open the board with the search field left blank.
2. Read the visible rows from the `Bugs` table and compare them with the seeded Open fixture set.

**Expected Results:**

1. The board page is visible. [07-AC1]
2. The `Search bugs by title` searchbox is empty. [11-AC1]
3. The `Open` state filter is selected by default. [13-AC3]
4. The `Bugs` table shows every seeded Open bug, including `Login fails`, `Issue with log-in`, `Search indexing delay`, and `Payment button disabled`. [07-AC2, 13-AC3]
5. The Closed bug `Login fixed` is not shown while Open is active. [13-AC4]
6. The page does not show `No bugs matched.` or `No bugs.`. [11-AC1]
7. The table contains all and only the bugs in the selected active Open state. [13-AC3, 13-AC4]
8. The test does not interpret the blank query as including Closed bugs; all bugs means all bugs in the selected state. [13-AC3]

#### 1.2. Filter bugs by title text and exclude nonmatching titles

**Preconditions:**

1. Authenticate with the seed and load the fixture set (see Seed / Fixture Guidance).

**Steps:**

1. Focus the `Search bugs by title` searchbox and type `login` one character at a time.
2. Replace the query with `fails`.

**Expected Results:**

1. Filtering updates while typing without a submit or navigation. [11-AC2]
2. The matching Open rows `Login fails` and `Issue with log-in` are visible. [11-AC2]
3. The Open rows `Search indexing delay` and `Payment button disabled` are not visible because their titles do not contain the query. [11-AC2]
4. The `Bugs` table remains visible and contains no nonmatching bug rows. [11-AC2]
5. After replacing the query with `fails`, only the Open row `Login fails` is visible. [11-AC2]
6. The row `Issue with log-in` is not visible. [11-AC2]

#### 1.3. Matches case-insensitively and normalizes whitespace

**Preconditions:**

1. Authenticate with the seed and load the fixture set (see Seed / Fixture Guidance).

**Steps:**

1. Enter `LOGIN` in the `Search bugs by title` searchbox.
2. Replace the query with extra surrounding and internal whitespace, such as `login   fails`.

**Expected Results:**

1. The title `Login fails` is visible, demonstrating case-insensitive matching. [11-AC3]
2. The title `Issue with log-in` is also visible when punctuation normalization applies. [11-AC3]
3. Nonmatching Open titles are absent. [11-AC2]
4. After replacing the query, the query is trimmed and repeated whitespace is collapsed. [11-AC3]
5. The `Login fails` row is visible despite the extra whitespace. [11-AC3]
6. The `Issue with log-in` row is not visible because the normalized query contains the additional word `fails`. [11-AC2, 11-AC3]

#### 1.4. Normalize punctuation so hyphenated and plain terms match the same titles

**Preconditions:**

1. Authenticate with the seed and load the fixture set (see Seed / Fixture Guidance).

**Steps:**

1. Enter `login` in the `Search bugs by title` searchbox with Open selected.
2. Replace the query with punctuation and whitespace around the term, such as `log-in`.

**Expected Results:**

1. The row titled `Login fails` is visible. [11-AC3]
2. The row titled `Issue with log-in` is visible because `log-in` normalizes to a title-searchable form matching `login`. [11-AC3]
3. The result contains only titles whose normalized text includes the normalized query. [11-AC3]
4. After replacing the query, punctuation and surrounding whitespace are normalized for the query. [11-AC3]
5. Both `Login fails` and `Issue with log-in` remain visible. [11-AC3]
6. The result is still title-based and does not broaden to description, owner, or severity fields. [11-OOS]

#### 1.5. Restrict search to title text only, excluding matches in description, owner, or severity

**Preconditions:**

1. Authenticate with the seed and load the fixture set (see Seed / Fixture Guidance), which includes `Search indexing delay` with `login` only in its description, `Payment button disabled` with `login` only in its owner, and `Payment button disabled` with severity `HIGH` while its title contains neither `login` nor `high`.

**Steps:**

1. Enter `login` in the `Search bugs by title` searchbox.
2. Replace the query with `high`.

**Expected Results:**

1. The fixture provides separate negative controls where the query term appears outside the title. [plan-only]
2. The negative-control titles themselves do not contain `login` or `high`. [plan-only]
3. `Login fails` and `Issue with log-in` are visible because their titles match. [11-AC2]
4. `Search indexing delay` is not visible even though its description contains `login`. [11-OOS]
5. `Payment button disabled` is not visible solely because its owner contains `login`. [11-OOS]
6. No row is included based only on description or owner. [11-OOS]
7. After replacing the query with `high`, `Payment button disabled` is not visible even though its severity is HIGH. [11-OOS]
8. No row is included based only on severity. [11-OOS]
9. The result is determined by title text only. [11-OOS]

#### 1.6. Show the "No bugs matched." message when no titles match the query

**Preconditions:**

1. Authenticate with the seed and load the fixture set (see Seed / Fixture Guidance), so bugs are present in the selected Open state.

**Steps:**

1. Enter a unique query such as `zzzz-no-title-match` in the `Search bugs by title` searchbox.

**Expected Results:**

1. The visible table body contains no bug rows. [11-AC6]
2. The board displays the exact message `No bugs matched.`. [11-AC6]
3. The board does not display `No bugs.`. [plan-only]
4. The `Bugs` table headers remain available unless the implementation intentionally replaces the table; no bug data row is present. [07-AC3]

#### 1.7. Clears search with the X control and restores the active-state board

**Preconditions:**

1. Authenticate with the seed and load the fixture set (see Seed / Fixture Guidance).

**Steps:**

1. Enter `login` in the `Search bugs by title` searchbox.
2. Click the `Clear search` control.

**Expected Results:**

1. The searchbox contains `login`. [11-AC2]
2. The `Clear search` control is visible and enabled. [11-AC4]
3. The board is filtered to matching Open titles. [11-AC2]
4. After clicking `Clear search`, the searchbox value is blank. [11-AC4]
5. The Open board is restored and all seeded Open bug rows are visible. [11-AC4, 13-AC3]
6. The Closed rows remain hidden because Open is still selected. [13-AC4]
7. The page does not show `No bugs matched.`. [11-AC4]

#### 1.8. Preserves sort order and sort indicator while searching

**Preconditions:**

1. Authenticate with the seed and load the fixture set (see Seed / Fixture Guidance).

**Steps:**

1. Click the `Title` column button until the `Title` column has the intended ascending order, and record the visible order of the seeded rows.
2. Enter `login` in the `Search bugs by title` searchbox.
3. Click the `Severity` column button to establish a different sort, then enter a query that matches multiple rows.

**Expected Results:**

1. The matching column header exposes `aria-sort="ascending"`. [10-AC2]
2. The visible rows are ordered by title ascending. [10-AC2]
3. The ascending sort indicator remains associated with the Title header. [10-AC2]
4. After entering `login`, only the matching Open rows are visible. [11-AC2]
5. The matching rows remain in the same title-ascending order as the filtered subset. [11-AC5]
6. The Title header still exposes `aria-sort="ascending"` and its sort indicator is unchanged. [11-AC5]
7. Typing the search does not reset the selected sort column or direction. [11-AC5]
8. After sorting by Severity and entering a query, the filtered rows follow the selected Severity sort order. [11-AC5, 13-AC5]
9. The Severity header retains its active `aria-sort` direction and indicator while the query changes. [10-AC4, 11-AC5]

#### 1.9. Combines Open and Closed state filtering with title search

**Preconditions:**

1. Authenticate with the seed and load the fixture set (see Seed / Fixture Guidance).

**Steps:**

1. With the searchbox blank, click the `Closed` state button.
2. Enter `login` in the `Search bugs by title` searchbox while Closed is selected.
3. Click the `Open` state button while keeping `login` in the searchbox.
4. Change the query to a term with no matching title in the selected state, then switch between Open and Closed.

**Expected Results:**

1. The Closed state is selected. [13-AC4]
2. Only Closed rows such as `Login fixed` and `Archive cleanup` are visible. [13-AC4]
3. Open rows are not visible. [13-AC4]
4. After entering `login` with Closed selected, only Closed bugs whose titles match `login` are visible, such as `Login fixed`. [13-AC6]
5. Open matches such as `Login fails` and `Issue with log-in` are not visible. [13-AC4, 13-AC6]
6. The result is the intersection of the selected state and normalized title query. [13-AC6]
7. After clicking `Open` while keeping the query, Open is selected. [13-AC3]
8. Open matching rows such as `Login fails` and `Issue with log-in` are visible. [13-AC6]
9. The Closed row `Login fixed` is not visible. [13-AC4]
10. The search query is preserved when the state changes. [13-AC6]
11. When the query has no match in the selected state, `No bugs matched.` is shown and there are no bug rows. [13-AC7]
12. Changing the state reevaluates the same query against the newly selected state. [13-AC6]
13. A state that has no matching title still shows `No bugs matched.` rather than rows from the other state. [13-AC7]

## Technical Information

### Seed / Fixture Guidance

Use `tests/seed.spec.ts` as the Playwright seed for every workflow. It authenticates as the `buggy` user and verifies navigation to `/board`. Each scenario should start from a fresh or reset data state so scenarios remain independent.

Following the `beforeEach`/`afterEach` pattern used by the delete-bug tests, each scenario's `beforeEach` must first clear the board via the `deleteAllBugs` helper (`tests/support/board-fixtures.ts`), then create the fixture set below individually via `createBug`, matching the `BugFixture` shape over the backend REST API. The matching `afterEach` must delete each created bug via `deleteBugIfExists`, so setup and teardown stay symmetric with the delete-bug tests rather than relying on a bulk seed/reset helper. Include at least these records, with unique IDs and descriptions where shown:

- Open: title `Login fails`, description `Authentication timeout`, severity `HIGH`, owner `buggy`.
- Open: title `Issue with log-in`, description `Login form validation`, severity `MID`, owner `qa-user`.
- Open: title `Search indexing delay`, description `The login owner cannot find results`, severity `LOW`, owner `qa-user`.
- Open: title `Payment button disabled`, description `Payment cannot be submitted`, severity `HIGH`, owner `login-owner`.
- Closed: title `Login fixed`, description `Closed authentication issue`, severity `LOW`, owner `qa-user`.
- Closed: title `Archive cleanup`, description `Old records`, severity `HIGH`, owner `buggy`.

The exact records may be created using the repository's established fixture strategy, but every scenario must know the expected titles, states, sort order, and IDs it asserts. Keep at least one Open and one Closed bug available for combined-filter checks. The two Open negative controls deliberately place `login` only in a description or owner, and `Payment button disabled` is a HIGH-severity negative control for a `high` query. For a true no-row state, use a query that matches no title while bugs still exist; this must produce `No bugs matched.`. `No bugs.` is reserved for a selected state with no bugs at all and should not be confused with a search miss.

### Locator Guidance

Prefer accessible Playwright locators: `getByRole('searchbox', { name: 'Search bugs by title' })`, `getByRole('button', { name: 'Clear search' })`, `getByRole('button', { name: 'Open' })`, `getByRole('button', { name: 'Closed' })`, `getByRole('table', { name: 'Bugs' })`, table rows, and column-header buttons named `ID`, `Severity`, `Title`, and `Owner`. Scope title and owner assertions to the `Bugs` table. Use row or cell text for bug identity, and use `aria-sort` on the relevant column header to verify the sort indicator rather than relying only on decorative arrow text.
